# Contributing to District AI for Android

## Layout

```
app/                     The application module: Compose screens under ui/, navigation,
                         the Telecom softphone and incoming calls, push, app links,
                         sign-in, and AppContainer, which wires everything together.
core/core-model/         API types (kotlinx.serialization) and the contract fixture tests.
core/core-network/       The HTTP client, the API interfaces, error-envelope mapping, and
                         EndpointParityTest.
core/core-auth/          Keystore-backed token storage and the refresh coordinator.
core/core-data/          Repositories and the active-workspace state.
core/core-designsystem/  Design tokens and primitive composables. No project dependencies.
core/core-media/         LiveKit behind the CallEngine interface.
build-logic/             Convention plugins (district.android.*).
contracts/               Server-generated API fixtures. Never edited by hand.
parity/                  Snapshot of the iOS client's endpoint list.
scripts/                 verify-release-minification.sh (CI), smoke-emulator.sh (the local
                         Maestro lane), and maintainer scripts that need the (private)
                         server running locally.
```

[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) has the longer version.

## Setup

JDK 21 and an Android SDK with platform `android-37.0` and build tools `37.0.0`. Set
`ANDROID_HOME`, or put `sdk.dir=/path/to/sdk` in `local.properties` (gitignored). Android
Studio works but is not required; everything below is plain Gradle.

## The inner loop

```sh
./gradlew :core:core-model:testDebugUnitTest                            # one module
./gradlew :app:testDebugUnitTest --tests '*ContactsScreenTest'          # one class
./gradlew detekt -PdetektAutoCorrect                                    # fix formatting
```

Unit tests run on the JVM. UI tests use Robolectric and the Compose test rule, so no device
or emulator is needed for anything CI runs. Tests never talk to the real service: HTTP is
exercised against MockWebServer, and response shapes come from `contracts/`.

## The whole local gate

This is exactly what CI's one job runs:

```sh
./gradlew detekt lintDebug testDebugUnitTest assembleDebug
# then: at least one test result must exist (CI sums every module's result XMLs)
./gradlew :koverLog :koverVerify
scripts/verify-release-minification.sh
```

A few things these gates are strict about, so they do not surprise you in review:

- **Lint runs with `abortOnError` and no baseline.** Fix the finding; if one genuinely cannot
  be fixed, disable that check by name with the reason written beside it in
  `build-logic/convention/src/main/kotlin/district.android.base.gradle.kts`.
- **Coverage floors only go up.** `LINE_COVERAGE_FLOOR` and `BRANCH_COVERAGE_FLOOR` in
  `build.gradle.kts` are set by decision, below the measured values with some headroom, so
  rounding drift does not red the build; the comment above them records the current
  measurement and the headroom. Raise them when coverage rises; do not lower one to make a
  build pass.
- **A new module must be added to the `kover { }` dependency list** in `build.gradle.kts`,
  or it is silently left out of the coverage measurement.
- **Release builds minify.** `assembleDebug` does not run R8, so a missing keep rule only
  shows up in `verify-release-minification.sh`. Add keep rules to `app/proguard-rules.pro`.

## Dependencies

Versions live in `gradle/libs.versions.toml` and every configuration is locked. After
changing a version, regenerate the lockfiles with the command in the "Regenerating the
lockfiles" note in `build.gradle.kts` and commit them in the same change. A raised version
without its lockfiles fails dependency resolution ("enforced by Dependency Locking"), and a
lowered one is silently overridden by the lock, so neither does what the diff says.
Dependabot regenerates every module's lockfile in its own pull requests, so a red one is a
real failure of the upgrade. The toolchain (AGP, Kotlin, Robolectric, the Gradle wrapper)
arrives one pull request at a time, outside the weekly group; see `.github/dependabot.yml`.

New dependencies are a supply-chain decision. `settings.gradle.kts` restricts where
dependencies may resolve from, and JitPack is admitted for one module only; do not widen that.

## API contract fixtures

`contracts/*.json` are generated by the server's test suite and copied here byte for byte.
They are decoded with `ignoreUnknownKeys = false`, so a new field on the server fails here
until the Kotlin type has it. If you are changing a response type, the fixture change comes
from the maintainers' server repository first. Do not hand-edit a fixture, and do not make the
decoder lenient to get past a failure.

## Commits and pull requests

Conventional Commits are not required. What is required is that the message says **why**,
not just what; the diff already says what. A good message names the thing that was wrong,
the evidence, and what would have caught it.

Pull requests run `.github/workflows/ci.yml`, and all of it must be green. Fork pull requests
run the same job: it uses no secrets.

## Comments

The code comments here explain why a line is the way it is, often because the obvious
alternative was tried and failed. Keep that up: if you change behaviour a comment describes,
change the comment in the same commit, and if you remove a guard, say in the commit message
what made it unnecessary.

## Reporting bugs

Use the bug report form. Include the app version (Android's App info screen shows it), the
device and Android version, and what you expected. Do not paste anything from a real workspace (names, phone
numbers, message content) into a public issue.

For anything security-relevant, do not open an issue. See [SECURITY.md](SECURITY.md).
